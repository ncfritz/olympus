# olympus-sdk
A TypeScript compatible SDK based on the `@ncfritz/olympus-model` and `@ncfritz/olympus-api` packages.

## Motivation
The motivation here stemmed from a few things:
1. The absolute lack of compatibility within the JS ecosystem.  NestJS and NextJS are great frameworks, but they
   DO NOT play nicely together.  The API and model use Nest's Swagger modules to provide an OpenAPI spec for each
   API, but the set of libraries used here are not compatible with NextJS.
1. I wanted the ability to change API paths without having to worry about constantly refactoring here.  Since the
   API paths are embedded into the controllers, they are not conveyed in any way in the model.  Even if I could get
   around the compatibility issues with NestJS and NextJS, this would require pulling the API package into each
   package that wanted to consume the API - which is just... well... bad.  Since the SDK relies on the OpenAPI spec,
   the paths are always upn to date - assuming that the spec has been generated for the latest version of the API.
1. I didn't want to have to continually package API wrappers for each package that consumed the API.  This takes
   care of that for me.

## How?
This package uses [Hey API](https://heyapi.dev/) for the client generation.  This is a double edged sword as that
package is constantly being updated and doesn't appear to be incredibly stable.  But, it looks like it is the best
thing out there at the moment.  This package takes in an OpenAPI spec and outputs generated code... yay!  But where
does the spec come from?  This is actually a multi-phase build:

`@ncfritz/olympus-model` --> `@ncfritz/olympus-api` --> `@ncfritz/olympus-sdk`

1. The `@ncfritz/olympus-model` build is just a standard build to generate the types needed by the API.
1. The `@ncfritz/olympus-api` build actually builds the OpenAPI spec for each major API segment.  This is accomplished
   via a Jest test that builds the API spec document in NestJS and writes it to a file.  See `apiSpecGenerator.spec.ts`
   in `@ncfritz/olympus-api`.  The spec document is written to `./dist/<API>-openapi-spec.json` and packaged with
   the `@ncfritz/olympus-api` bundle.  This is then consumed by this package as a dev dependency.
1. This package generates the SDK using Hey API's toolchain:
   1. Each API to be generated needs to have it's own config file.  These are located in `config` at the root of the
      project.
   1. The SDK is generated by running `openapi-ts -f config/<API>.ts`.
   1. There is a target defined for each API in `package.json`.  These are chained together in the `prebuild` target.

## Important Notes
1. There is no `src` directory checked into version control.  What!?  This is omitted because all the source here
   is generated, so, what's the point to having it in version control?
1. This package uses multiple exports - one per API.  This may mean that you need to use the following options in
   your `tsconfig.json`:
   1. `"module": "esnext"`
   1. `"moduleResolution": "bundler"`

   With this, comes the need to specify that you are using imported types as types... so `import { type Blah } from @ncfritz/olympus-sdk/<API>`.
   Again... yay!
1. Dates are NOT automatically unmarshalled.  Why?  Simple, this package is mean to be used in an in-opinionated
   manner.  The front-end used `luxon`, the back-end uses `moment`... deal with it.

## Adding a new API
1. Update the `apiSpecGenerator.spec.ts` to ouput the spec for the new API.
1. Buold `@ncfritz/olympus-api`.
1. Add a new config in the `config` directory.  Copy an existing one and simply replace the API name so it matches the
   spec file you are referencing.
1. Add a new target in `package.json` that references the new config:
   ```
    "gen-<API>": "openapi-ts -f config/<API>.ts",
   ```
   and then add it to the `prebuild target` - i.e. `... & npm run gen-<API>`
1. Add  anew block to the `exports` section in `package.json`:
   ```json
   ...
   "exports": { 
     ...  
     "./<API>": {
        "types": "./dist/<API>/index.d.ts",
        "default": "./dist/<API>/index.js"
     }
   },
   ...
   ```
1. Run `npm run build`
1. Profit!
